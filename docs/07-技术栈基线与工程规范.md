## 3. 架构边界

### 3.1 单一事实源

- PostgreSQL：业务数据、Document AST、任务/编排状态、审批、Outbox/Inbox 的权威源；
- 现有企业知识库：公司正式知识的权威源；
- S3：原始附件、解析产物、导出文件、图片资源；
- Redis：可重建/可丢失的缓存与限流状态；
- RabbitMQ：任务运输层，不是任务事实源。

### 3.2 知识检索双链路

```text
Knowledge Gateway
  ├─ Existing KB Adapters → 现有企业知识库（不强制重建向量）
  └─ Workbench Attachment Retrieval
       ├─ BGE-M3
       ├─ pgvector
       ├─ PostgreSQL FTS + jieba 企业词典
       └─ bge-reranker-v2-m3 / FlagEmbedding
```

两条链路统一在 Evidence Builder 中做权限、版本、权威性、去重、冲突与引用定位处理。

### 3.3 异步编排边界

```text
FastAPI 事务
  ├─ 更新 Orchestrator State
  └─ 写 Outbox
        ↓
Outbox Dispatcher
        ↓
RabbitMQ quorum queue
        ↓
Celery Worker
        ↓
幂等执行 + 回写 PostgreSQL
```

Celery Beat 单活用于周期触发和补偿扫描；暂停点、审批点、超时与任务依赖均由 PostgreSQL 状态机表达。

## 5. 版本与依赖管理

- Python：3.12 基线，`uv.lock` 锁定；
- Node.js：项目冻结 LTS 版本，`pnpm-lock.yaml` 锁定；
- API：Pydantic Model + OpenAPI 为契约源，破坏性变化必须升版本；
- Database：Alembic revision；
- AST/Form：独立 `schema_version`；
- Prompt/Model Profile：独立版本；
- Helm/容器：不可变镜像 tag/digest 用于发布追溯。

---

## 6. 替换原则

允许企业已有能力替换以下默认实现：Keycloak 的上游 IdP、SeaweedFS、CloudNativePG、模型 Provider 等，但必须满足：

1. 保持对应标准协议/契约（OIDC、S3、PostgreSQL、OpenAI-compatible/Provider Adapter 等）；
2. 不降低 RBAC/ABAC、Evidence、Audit、RPO/RTO 和数据分级要求；
3. 完成接口、性能、故障恢复和安全验收；
4. 通过 ADR 记录替换原因和回退方案。

---

## 7. 明确不采用的默认方案

V1.1 一期不再默认：

- Rust/Java/Go 作为核心业务服务候选；
- MinIO 作为自建对象存储缺省实现；
- WebSocket 作为任务进度必选协议；
- Redis/Celery result backend 作为任务/审批事实源；
- 为接入工作台而强制重建现有企业知识库向量；
- Tiptap 商业云服务/商业插件作为基础依赖。
